# Case study: ATM10 on the M720q

**Objective:** move an existing Prism Launcher single-player world to a dedicated Ubuntu host while preserving the shared progress of a small group.

**Recorded environment:** Lenovo M720q, i5-8500T, 16 GB DDR4, Java 21, ATM10 v8.2 and NeoForge. The owner reported successful gameplay, with slowdowns when three players generated new terrain.

## 1. Match the server pack to the existing world

The setup used `ServerFiles-8.2.zip` to match the existing ATM10 v8.2 instance. Changing the modpack while migrating would combine two separate risks: moving the save and changing the software that interprets it.

The save was archived from Prism Launcher and transferred to Linux. The command below retains the recorded workflow with a placeholder for the address:

```powershell
scp ".\ATM10-World-Backup.zip" rob@ATM10_HOST:/home/rob/
```

`ATM10_HOST` is a placeholder. The complete save was retained so builds, player inventory, quests, and modded dimensions could move together. Keep the original single-player save as rollback material until the destination is validated.

## 2. Runtime and memory allocation

The historical heap settings were:

```text
-Xms8G -Xmx10G
```

These are Java arguments, not a shell command. They leave memory outside the heap for the operating system, filesystem cache, and JVM overhead. The final service-managed launcher must retain the NeoForge argument files generated by the matching server pack; a generic `java -jar` replacement is not equivalent.

The working directory was `/opt/minecraft/atm10/`. The chat first used a tmux session named `atm10`, then moved toward systemd management with `atm10.service` and RCON-based shutdown.

```bash
# Reconnect to the historical interactive console, when that session exists.
tmux attach -t atm10

# Inspect the service-managed deployment.
systemctl status atm10 --no-pager -l
sudo journalctl -u atm10 -n 50 --no-pager
```

Do not start a second manual server while the systemd instance is running. The deployed unit and shutdown helper should be captured before treating a reconstructed example as the exact production configuration.

## 3. Diagnose startup exits before changing memory

The setup encountered a server exiting during startup. The investigation separated application crashes from systemd termination and checked service state and logs. It also found a startup script pasted underneath the existing generated script, rather than replacing the intended content.

The lesson is to inspect the launcher and logs together. A restart policy cannot correct a malformed script, an incorrect working directory, or a stop helper that runs at the wrong time.

## 4. Investigate the exploration slowdown

The owner reported that ATM10 ran well until three players generated chunks. The following diagnostic commands appeared in that investigation:

```bash
lscpu | grep "Model name"
free -h
ps -eo pid,rss,%cpu,args --sort=-rss | head -8
pgrep -af java
jcmd -l
```

For the identified Minecraft JVM:

```bash
# Replace JAVA_PID with the current Minecraft process ID.
jcmd JAVA_PID GC.heap_info
top -H -p JAVA_PID
```

`jcmd` requires suitable JDK tools and permission to attach to the process. The investigation initially used a stale process ID; after the JVM restarted, the PID had changed. Rediscover the process rather than assuming the old PID is still valid.

| Historical observation | Interpretation |
| --- | --- |
| About 14 GiB usable system RAM | Installed memory and OS-visible memory differ |
| About 4 GiB available | Low completely-free memory alone did not establish exhaustion |
| About 10.3 GiB process RSS | Includes memory outside the Java heap |
| About 3.55 GiB heap used, 10 GiB maximum | Idle heap use did not justify a larger allocation |
| Slowdowns during concurrent exploration | Chunk generation warranted profiling under load |

The recommendation was to retain the 10 GiB maximum and investigate chunk generation. A pregeneration tool was discussed, but completion is not established. No benchmark improvement or sustained TPS result is claimed here.

## 5. Backup-service investigation

The older transcript includes these checks:

```bash
sudo systemctl status atm10-backup.service --no-pager -l
sudo journalctl -u atm10-backup.service -n 50 --no-pager
ls -ld /opt/minecraft/backups
ls -ld /opt/minecraft/atm10/world
systemctl is-active atm10
```

The presence of a service and an attempted backup is different from a successful recurring backup. Verify the last exit status, archive contents, retention, off-host copy, and a test restore before declaring protection complete. RCON credentials and raw service environments are excluded from this repository.

## Engineering decisions

- Allocate the stronger CPU to the more demanding workload.
- Match software versions during a world migration.
- Use application-aware shutdown rather than relying on abrupt termination.
- Measure heap use and available RAM before changing JVM limits.
- Treat player testing, backup integrity, and restore testing as separate checks.
